# Portfolio (Japanese / English)

Static site for https://sabstha.github.io — Japanese at `/`, English at `/en/`.
No dependencies: `node` 20+ only.

```
npm test          # rule tests
npm run validate  # privacy scan, approvals, JA/EN completeness, [[CONFIRM]] markers
npm run build     # → dist/ (scans the built HTML again)
npm run check     # all three
node tests/browser.mjs http://127.0.0.1:5201   # real-browser checks against a served dist/ (also in CI)
```

Design: "drill report" — midnight hero band with a real restore-drill report as the signature,
cool light body, one cobalt accent; green/red only for real pass/fail. Bricolage Grotesque (display),
Noto Sans JP (body), JetBrains Mono (data). Skills are chips by evidence level. Light/dark
(system default, toggle remembered). Architecture diagrams are HTML
(`scripts/diagrams.mjs`), not images, so they reflow on phones and are readable by screen readers.
Strict CSP: the only script is the theme toggle (`site/site.js`); no analytics, no trackers.

## What is published

| Source | Who edits | Reaches the site when |
|---|---|---|
| `content/profile.json` | by hand | `confirmed: true` projects only; no `[[CONFIRM …]]` left |
| `content/case-studies/<slug>.{en,ja}.md` | by hand | both languages exist and pass the privacy scan |
| `content/articles/<slug>.{en,ja}.md` | by hand | both languages, a `<!-- date: YYYY-MM-DD -->` line, privacy scan |
| `content/published.json` | generated by Cloud Career HQ → **Publish** | item was approved in the app and passes `scripts/rules.mjs` |

Records in Cloud Career HQ are **private by default**. Only items you approve one by one are
exported, and only whitelisted public fields (title, summary, links, status, dates, issuer,
verification). Notes, job applications, contacts and anything else never leave the app.
Editing an approved item turns it back to "changed" until you approve it again.

## Publishing a change

1. In Cloud Career HQ → Publish, approve the items, then **Download export**.
2. `npm run propose -- ~/Downloads/portfolio-content-YYYY-MM-DD.json`
   (validates, commits to a new `content/…` branch, prints the PR link).
3. Push the branch and open the PR. CI runs tests, validation and the build.
4. **Merging the PR is the approval.** The push to `main` deploys to GitHub Pages.

Any failed check (private data, missing translation, unapproved item, CONFIRM marker) blocks
the deploy. Keep `main` protected so changes arrive only through PRs.

## Rules for content

- Only list work that can be demonstrated; say what is not finished.
- Implementation is AI-assisted: describe your role (requirements, review, verification).
- Never: employer details, customer names, revenue, server IPs, private repos, credentials.
- Certifications appear only with a public verification URL (e.g. Credly).
