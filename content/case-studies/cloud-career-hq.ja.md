# Cloud Career HQ

**転職活動を管理するための、費用ガード付きの非公開AWSアプリケーション**

現状：承認手順を経て、**2026年11月7日にAWS（東京リージョン）へデプロイしました。** 実際のアプリは非公開でサインインが必要なため、下記リンクは[架空データの公開デモ](https://sabstha.github.io/cloud-career-hq-demo/)です。

## 課題

サポート職からクラウドインフラへキャリアを移すには、次のような多くの情報を同時に管理する必要があります。
- 求人とその実際の要件
- 実際に証明できるスキル
- 資格、検証プロジェクト、学習メモ
- 次に何を学ぶべきか

スプレッドシートでは、「志望する求人の要件のうち、今の時点で根拠を示せるものはどれか」という最も重要な問いが見えにくくなっていました。

## 主な機能

- **求人管理**：求人と要件を登録し、重複を警告します。給与やリモート可否など記載のない情報は推測せず「記載なし」と表示します。
- **ルールベースの準備度評価**：要件を「達成」とみなすのは、検証済みで有効期限内の証拠、またはリポジトリやドキュメントへのリンクがある完了済みプロジェクトがある場合のみです。自己申告は「一部達成」扱いです。AIによるスコアや根拠のない確率は使いません。
- **証拠・プロジェクト・学習記録・スキル・LinkedIn投稿の下書き**を相互に関連付けて管理します。
- **JSONのエクスポート／インポート**：構造を検証し、不正なファイルでデータが上書きされることはありません。
- **公開機能**：記録は既定で非公開です。項目ごとに自分で承認し、許可した項目だけをこのポートフォリオへ書き出します。承認後に内容を変更した場合は再承認が必要です。

## アーキテクチャ（AWS 東京リージョン）

| 層 | サービス | 主な設定 |
|---|---|---|
| 認証 | Amazon Cognito（Liteティア） | 管理者のみがユーザーを作成、TOTPによるMFA必須、12文字以上のパスワード、トークン有効期限60分、ゲストIDは無効 |
| API | AWS AppSync（GraphQL） | Cognitoユーザープールのみ（APIキーなし）、全モデルが所有者限定、所有者フィールドは変更不可 |
| データ | Amazon DynamoDB（オンデマンド、9テーブル） | ポイントインタイムリカバリ有効。本番テーブルは削除保護・保持設定・破壊的なスキーマ変更を禁止 |
| バックアップ | EventBridge Scheduler → Lambda → S3 | アプリのインポート形式で日次エクスポート。非公開・バージョニング有効・TLS必須のバケット |
| 監視 | CloudWatch → SNS → メール | 5つのアラーム（APIエラー、拒否リクエストの急増、バックアップ／求人検索／費用レポートの失敗）と、定期ジョブの実行も確認する日次の費用メール（SES） |
| 求人検索 | EventBridge Scheduler → Lambda → OpenAI | 日次のWeb検索で求人を収集・確認・分析。手動実行は1日2回まで、月額上限は5米ドル |
| 費用 | AWS Budgets → SNS → Lambda | 費用ガード（後述） |
| ホスティング | Amplify Hosting | デプロイのたびにテストとインフラ検証を実行。セキュリティヘッダー（CSP、HSTS） |

すべてAmplify Gen 2（AWS CDK）によるコードで定義しています。

## セキュリティ上の判断

- **認可はUIではなくバックエンドで強制します。** 生成されたリゾルバーのコードで、次の2点を確認しました。すべてのクエリとミューテーションでレコードの所有者と呼び出し元のCognito IDを照合していること、そして所有者フィールドを呼び出し元が設定できないことです。
- **公開サインアップなし、全員MFA必須。** 一人で使う非公開アプリのため、自己登録は攻撃面を増やすだけです。
- **誤操作からデータを守ります。** 35日間のポイントインタイムリカバリ、データベース外への日次エクスポート、本番データの保持設定と削除保護を組み合わせています。
- **最小権限。** バックアップ関数はテーブルの読み取りとS3の1つのプレフィックスへの書き込みのみ、費用ガードは1つのAmplifyブランチと1つのユーザープールのみを操作できます。
- **フロントエンドとリポジトリに秘密情報を置きません。** 公開パイプラインは、書き出し時とCIの2回、公開項目にメールアドレス・電話番号・IPアドレス・キー・トークンが含まれていないかを検査します。

## 検証：まずオフライン、次に実際のAWSで

AWSに費用をかける前に、設計が正しいという根拠を得ることを重視しました。

- **24項目のインフラ検証**：実際のデプロイで使われるCloudFormationを、AWSアカウントなしでローカル生成して検査します。MFA、APIキーがないこと、所有者限定のリゾルバー、PITR、バケットポリシー、アラーム、予算設定、各関数の権限を確認します。
- **142件のユニットテスト・UIテスト**：ユーザー間の分離（他のユーザーがレコードを読む・変更する・削除する・所有権を奪うことができない）、バックアップから復元への往復、未同期変更の再試行と再開、公開ルールを含みます。
- **15項目の実ブラウザE2Eテスト**を公開デモに対して実行しています：全モジュールでの作成・編集・検索・削除、エクスポート／インポート、保存データ破損からの復旧、2タブ間の同期、幅390pxのモバイル表示。

これらは本番デプロイのたびに再実行されます。そのうえで、実際のAWS上の一時的な環境で次を実施しました。

- **ユーザー間分離テスト：9/9合格**（デプロイしたAPIに対して実施）
- **復元訓練：7/7合格**（データ作成 → バックアップ → 削除 → 復元 → 比較）。初回の訓練で、**オフラインのテストでは見つからなかった実際の不具合を発見しました。** すべての保存が `Unauthorized on [id]` で拒否されていました。原因は、`owner` のフィールド単位の認可ルールによってAppSyncが入力フィールドをすべて検査するようになり、暗黙の `id` がその許可リストに含まれていなかったことです。フィールドを1つ明示的に定義して修正し、再発防止の検証項目を追加しました。
- **アラーム訓練と費用ガード訓練に合格。** ガードはテストユーザーを無効化し、その後再有効化しました。データは削除していません。

稼働初日の教訓：データ欠損を失敗とみなす「ジョブ未実行」アラームは、最初の定期実行の前に誤検知しました。これを日次メール内の確認に置き換えました。

## 費用と「予算は上限ではない」こと

想定費用はクレジットなしの定価で**月額約3.2米ドル（約485円）**で、その約63%はビルド時間です。日次メールで、残りのクレジット、カードへの請求額、クレジット失効までの日数を確認でき、失効の30日前からはアプリ削除のリマインダーが届きます。

AWS Budgetsは支出を止めません。請求データは8〜24時間遅れて届くため、限界を明記した**費用ガード**を設計しました。

- **動作**：月間予算の200%（約2,000円）に達すると、Lambda関数がサイトをロックし、自動ビルドを停止し、全ユーザーを無効化してサインアウトさせます。データは削除しません。
- **できないこと**：すでに発生した支出の取り消しや、発行済みのアクセストークン（最大60分有効）の無効化はできません。ストレージ・バックアップ・アラームは月数セント程度の課金が続きます。

この限界を文書化することも設計の一部です。安全に見えるだけのガードは、ガードがないよりも危険だと考えています。
